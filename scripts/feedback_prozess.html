Von der Eingabe bis zum Feature dauert es typischerweise eine Session (< 2 h).

Schritt für Schritt

💬  Schritt 1 – Nutzer sendet Feedback

Der eingeloggte Nutzer klickt den Feedback-Button (fixed, unten links in der App) und wählt eine Kategorie: Fehler · Feature-Wunsch · Allgemein · Sonstiges. Die Eingabe ist auf 2.000 Zeichen begrenzt.

⚙️  Schritt 2 – API speichert & versioniert

Der POST-Request landet bei /api/feedback. Die API speichert parallel in zwei Wegen: (a) in die Supabase-Datenbank (Tabelle feedback, mit workspace_id + user_id) und (b) als Git-Commit direkt in die Datei feedback.md im Repository – via GitHub Contents API. Jeder Eintrag bekommt eine fortlaufende ID (F-001, B-002 …).

📄  Schritt 3 – feedback.md im Repository

Die Datei ist eine strukturierte Markdown-Datei mit einem Eintrag pro Feedback. Format: ID | Timestamp | Kategorie, Workspace, Nutzer-E-Mail, Nachricht. Gelöste Einträge bekommen den Marker Status: bearbeitet. So ist der komplette Feedback-Verlauf versioniert und nachvollziehbar.

📲  Schritt 4 – Telegram-Reminder via Watchtower

Watchtower überwacht das Repository auf neue Commits in feedback.md. Sobald ein neuer Feedback-Commit landet, schickt Watchtower automatisch eine Telegram-Nachricht an den Entwickler – mit Kategorie, Workspace und Nachricht. Kein manuelles Polling nötig, der Push-Kanal sorgt für sofortige Benachrichtigung.

🤖  Schritt 5 – Claude liest & priorisiert

Beim nächsten Session-Start liest Claude die feedback.md automatisch aus (über den Kontext-Inject oder manuell per „Gibt es neues Feedback?"). Claude priorisiert nach Häufigkeit, Workspace-Relevanz und technischer Machbarkeit – und schlägt vor, welche Punkte er als nächstes umsetzt.

🚀  Schritt 6 – Implementierung & Release

Claude implementiert das Feature direkt im Repo, erstellt einen Commit und pusht auf den Development-Branch. Der GitHub Actions Workflow deployed automatisch auf den Produktiv-Server. Abschließend wird der Feedback-Eintrag auf Status: bearbeitet gesetzt und ein Update-Eintrag in DashboardUpdates.tsx veröffentlicht – sichtbar für alle Nutzer im Dashboard.

Tipps aus der Praxis

Kleiner Button, große Wirkung. Der Feedback-Button ist fixed unten links platziert – immer erreichbar, nie im Weg. Nutzer senden Feedback genau dann, wenn etwas auffällt.
Git als Single Source of Truth. feedback.md liegt im Repo – Claude sieht es ohne extra Tooling. Kein Jira, kein Trello, kein Webhook nötig.
Push statt Poll. Watchtower + Telegram sorgt dafür, dass der Entwickler sofort benachrichtigt wird – kein manuelles Nachschauen in der feedback.md.
Denormalisierter Kontext. Workspace-Name und E-Mail direkt im Eintrag speichern (nicht nur IDs). Claude muss keine Joins machen, sieht den vollen Kontext sofort.
Resilient by design. API speichert immer in beide Wege (DB + GitHub). Wenn einer fehlschlägt, landet das Feedback trotzdem irgendwo.
Transparenz für Nutzer. Die Dashboard-Updates-Sektion zeigt Titel, Datum und Beschreibung jedes neuen Features – Nutzer sehen, dass ihr Feedback ankommt.
